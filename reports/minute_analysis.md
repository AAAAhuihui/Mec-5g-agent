# Redis 记忆读取测评结论

## 结论

本次在 VMware 虚拟机的实际 MySQL 8.4 与 Kubernetes Redis 7-alpine 上完成了 2,400 次计时读取。主测包含 50 个隔离会话、语义摘要、任务摘要、重要事件和完整 `get_or_create_memory()`，覆盖 cold、warm、mixed，以及并发 1 和 5。

- 主测读取：2,400/2,400 成功，错误 0，结果不一致 0。
- 专项检查：34/38 通过。四个失败均为“数据库写入成功、缓存写入失败、Redis 恢复后继续命中旧值”。
- 单接口热缓存的平均延迟降低约 21.3–29.0 倍（串行），并发 5 时降低约 7.6–9.2 倍。
- 完整记忆 warm/mixed 的平均延迟稳定降低约 1.31–1.33 倍；SQL 执行尝试和连接尝试均减少 25%。
- cold 场景基本无收益，摘要和事件单接口通常因一次 Redis miss 增加少量开销。
- 重要事件 mixed 只有 64%–66% 业务命中率，平均延迟改善约 2.16–2.70 倍，但 P95 几乎没有改善。

因此，Redis 对高频重复读取两个摘要和固定问题的重要事件很有效；对完整记忆加载的收益受到其他未缓存 MySQL 路径限制。现有故障恢复一致性不能通过，不能只展示加速数字。

## MySQL 访问变化

- 单个摘要或重要事件未命中：每次约 15 条 SQL、3 次连接；命中时降为 0。
- 完整记忆 A：每次约 120 条 SQL、24 次连接。
- 完整记忆 warm/mixed B：每次约 90 条 SQL、18 次连接，即均减少 25%。

这些数值不是正常业务 SELECT 的理想数量。当前每个存储函数都会调用 `ensure_schema()`，因此一次逻辑读取包含建库/建表检查和 `information_schema` 查询。最直接的后续性能优化是把 schema 初始化迁移到应用启动或迁移阶段，再引入 MySQL 连接池；这可能比继续增加摘要缓存更能改善完整记忆读取。

## 故障恢复问题

正常主测没有错误或内容不一致，TTL、显式失效、Redis 读取超时回源和服务恢复检查也通过。唯一失败路径为：

1. MySQL 更新成功；
2. Redis `SET` 或事件版本递增失败，但缓存层吞掉异常；
3. Redis 恢复后，旧键仍存在；
4. 下一次读取直接命中旧摘要/旧事件，不再回源。

semantic、task、events、完整 memory 均复现了该问题。可选优化是让缓存写入返回成功状态，并配合事务外盒（outbox）或可靠失效重试；仅靠 TTL 只能限制陈旧时间，不能保证写后读一致性。

## 测试边界

- 实际总耗时 1951.225 秒，即 32 分 31 秒；包含种数、每组预热、oracle 和专项检查，计时读取为 2,400 次。
- 测试客户端运行于同一 VMware 虚拟机的临时 Docker 容器，通过 host network 访问 Kubernetes Service ClusterIP；容器限制 2 CPU、1 GiB 内存。
- 使用项目现有 Agent 镜像 `mec-5g-rag-agent:0.1.0`、MySQL 8.4 和 Redis 7-alpine；不调用 LLM。
- 这是单轮合成负载，A/B 的函数正确性和差距可信，但不适合把最后一位小数写进简历。正式表述应使用保守范围。
- mixed 使用约 80% 热点会话、70% 固定问题，每 20 次读取前做一次更新；摘要采用 write-through，因此其 mixed 命中率仍为 100%。
- 主测返回一致不等于 Agent 回答质量提升，也不能推导 LLM Token 或端到端回答耗时。

## 建议简历口径

可以写：

> 基于 MySQL + Redis 构建分层会话记忆，并设计 50 会话、2,400 次读取的隔离 A/B 测评；热缓存下摘要/固定查询事件读取延迟降低一个数量级以上，完整记忆装配平均延迟降低约 24%，同时减少约 25% 数据库访问；覆盖 TTL、失效、回源与一致性检查。

不要写“所有场景均提升 20 倍”，因为 cold 无收益，重要事件 mixed 的 P95 也未改善。若尚未修复故障恢复旧缓存问题，面试时应将它作为测试发现和后续优化方向说明。
